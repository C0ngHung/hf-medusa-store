## 0. Architecture decision — one unified discount-code module (supersedes the earlier open question)

**There is exactly one customer-facing discount-code module**, not a generic `DiscountCode` component sitting beside a separate VoucherEngine-only panel. Medusa's storefront already ships a Promotion Code UI in the cart/checkout summary (`discount-code/index.tsx`, audited in §1.2 below); VoucherEngine's discount is carried into `cart.promotions`/`cart.total` through an **ephemeral, cart-specific Medusa Promotion** (SPEC Decision G), so the existing Promotion Code UI is the natural single surface to extend, not duplicate.

- **The existing promotion UI is enhanced/reworked in place, not duplicated.** The component today called `DiscountCode` is extended to also understand VoucherEngine codes — referred to elsewhere in these docs as `EnhancedDiscountCode` (equally acceptable: `PromotionCodeModule`, or "`DiscountCode` with Voucher Engine support"). There is one input, one Apply button, one applied-codes list for both generic promotions and vouchers.
- **VoucherEngine's own business logic is not implemented by overriding the backend Promotion module.** VoucherEngine remains its own module: it owns code validation (V1–V8), discount calculation, the global cap, usage/audit logging, and rate limiting. Medusa's Promotion module is used only as the mechanism that carries an already-computed discount amount into `cart.promotions`/`cart.total` (the ephemeral Promotion, Decision G) — VoucherEngine does not redefine or fork Promotion module behavior. This is a backend architecture fact this document assumes, not something the storefront UI implements — but it is the reason the storefront doesn't need a parallel discount surface: the Promotion module (and its existing UI) is the shared carrier both features already use.
- **Frontend consumes the existing promotion UI surface; backend uses Promotion only as a carrier.** These are two ends of the same fact: the storefront's `cart.promotions` array already contains VoucherEngine's discount (via the ephemeral Promotion) whether or not any voucher-specific UI exists — so the enhanced module's job is to (a) render generic promotions from `cart.promotions` as today, and (b) recognize and specially render the one entry that's actually a voucher, using data from `cart.metadata.voucher` instead of that entry's own (internal, non-human) fields.
- **Active voucher display is hydrated from `cart.metadata.voucher`, not `cart.promotions`.** The ephemeral Promotion's own `code` is an internal, system-generated string (e.g. `VEPH-...`) that must never reach the customer. `cart.metadata.voucher` carries the human voucher `code`, the discount amount, and the capped flag — this is what the module reads to decide "is a voucher active" and what to show for it.
- **Generic promotions are read from `cart.promotions`, minus the ephemeral entry.** The module filters out the one `cart.promotions` entry whose `id` equals `cart.metadata.voucher.ephemeral_promotion_id` before rendering the generic-promotion rows — every other entry renders exactly as `DiscountCode` renders it today.
- **When generic promotion codes are changed, the ephemeral voucher promotion must be preserved.** Applying or removing a _generic_ code resubmits the full `promo_codes` array to the existing full-array-replace call; that resubmitted array must still include the ephemeral voucher's internal code (it is excluded only from what's _displayed_, never from what's _sent_), or an unrelated generic-code edit would silently detach the active voucher.
- **Voucher apply/remove/replace still go through VoucherEngine's own endpoints**, unchanged from the original audit:
  - `POST /store/carts/:id/voucher` — apply.
  - `POST /store/carts/:id/voucher?replace=true` — confirmed replacement of an already-active voucher.
  - `DELETE /store/carts/:id/voucher` — remove.
  - `GET /store/customers/me/vouchers` — "Available vouchers" list.
- **UI copy is English; backend `customer_message` is still shown verbatim.** All UI-authored strings (labels, buttons, placeholders) are English going forward. Any string the backend actually returns (`customer_message`, `cap_explanation`, the replace-confirmation prompt, the remove-success message) must still be displayed exactly as received — currently that means Vietnamese text in production, since no backend copy was changed. Do not translate a backend-supplied string client-side.

This section supersedes §3/§4's earlier "should 'Available vouchers' reuse the existing `DiscountCode` component, or be separate?" open question — see the corresponding rows in §3/§4 below, now marked Resolved.

## 1. Storefront audit summary

### 1.1 Framework & routing

- Next.js 15.5.18, React 19, App Router only. Dev server on port 8008.
- Routes: `src/app/[countryCode]/(main)/cart/page.tsx` (cart), `(checkout)/checkout/page.tsx` (separate layout, no nav/footer).
- Next 15 async-params convention throughout (`params: Promise<{countryCode}>`) — any new voucher-related page must follow this.
- `src/middleware.ts` sets `_medusa_cache_id` cookie used to namespace cache tags — relevant to voucher cache invalidation.

### 1.2 Current Cart page structure

```
cart/page.tsx (Server Component)
 └─ modules/cart/templates/index.tsx (CartTemplate)
     ├─ sign-in-prompt (guest only)
     ├─ templates/items.tsx → components/item/index.tsx (per line)
     ├─ modules/suggestions/templates/cart-suggestions (Suspense-streamed, unrelated feature)
     ├─ templates/summary.tsx (Summary, "use client")
     │   ├─ modules/checkout/components/discount-code/index.tsx  ← existing promo UI, TO BE
     │   │                                                          ENHANCED in place (§0) — not
     │   │                                                          duplicated alongside a new panel
     │   ├─ modules/common/components/cart-totals/index.tsx
     │   └─ Button → /checkout
     └─ empty-cart-message
```

- **`discount-code/index.tsx`** (verified in full, `hf-medusa-store/apps/storefront/src/modules/checkout/components/discount-code/index.tsx`) is the only existing discount UI, and — per §0 — the component this feature enhances rather than sits beside. It operates purely on `cart.promotions` (generic Medusa promo codes) via **full-array replace**: `applyPromotions(codes: string[])` → `sdk.store.cart.update(cartId, { promo_codes: codes })` (`src/lib/data/cart.ts:258-279`). There is no "remove one code" endpoint used today — removal re-submits the array minus one code. The enhanced version must preserve this full-array-replace mechanism for generic codes while ensuring the ephemeral voucher code always survives the resubmission (§0).
- `cart-totals/index.tsx` already renders a conditional **Discount** row keyed off `discount_subtotal` (`data-testid="cart-discount"`), and takes a loose totals-shaped prop, not a full `HttpTypes.StoreCart` — reusable as-is, unaffected by this feature.
- **Mini-cart (`layout/components/cart-dropdown/index.tsx`)** shows subtotal only — **no discount/voucher visibility at all** in the mini-cart today. Out of scope for this feature (see §4 item 7).
- Dead code found in `src/lib/data/cart.ts`: `applyGiftCard`, `removeDiscount`, `removeGiftCard` (lines 281-322) are commented-out no-ops from an abandoned design; `submitPromotionForm` (324-334) is defined but never called (dead).
- `data-testid`s already present on the existing promo UI (`discount-input`, `discount-apply-button`, `discount-row`, `remove-discount-button`, etc.) suggest a prior/planned e2e convention. Since the component is being enhanced in place rather than replaced, these test ids can likely be kept or extended rather than invalidated wholesale — an implementation-time decision, not a design blocker.

### 1.3 Design system & reusable components

- **No `@medusajs/ui` package** — only `@medusajs/ui-preset` (Tailwind tokens) and `@medusajs/icons`. The team ships a **custom local kit** at `modules/common/components/ui/index.tsx`: `Text`, `Heading`, `Button` (variants `primary|secondary|transparent`, `isLoading`), `Container`, `Badge` (colors `green|red|blue|orange|grey|purple`), `Input`, `Label`, etc., built with `clsx` (re-exported as `clx`).
- Line 13 of that file: `// TODO: Add Toaster component back when needed for notifications` — **there is no toast component today.**
- `tailwind.config.js`: Medusa-preset custom breakpoints `2xsmall(320)/xsmall(512)/small(1024)/medium(1280)/large(1440)/xlarge(1680)/2xlarge(1920)` — default Tailwind `sm/md/lg` names are not used. `small:` ≈ desktop.
- `tailwindcss-radix` + `@radix-ui/react-accordion` are present as deps (unused by cart today) — available if a collapsible applied-codes list is wanted, though not required by the current design.

### 1.4 Cart state & API-client patterns

- All cart mutation logic lives in `src/lib/data/cart.ts` (`"use server"`). Pattern every new voucher action must follow:
  - SDK instance: shared `sdk` from `src/lib/config.ts` (auto-injects `x-medusa-locale`) — **never instantiate a second client.**
  - Cart id: cookie `_medusa_cart_id` (`src/lib/data/cookies.ts:112-132`), not an `x-session-id` header.
  - Auth: `getAuthHeaders()` reads `_medusa_jwt` cookie → `Authorization: Bearer` or `{}` for guests.
  - Cache: reads use `next: { tags: [...] }` + `cache: "force-cache"`; every mutation calls `revalidateTag(await getCacheTag("carts"))` (and often `"fulfillment"` too, since promotions can affect shipping options).
  - Errors: every SDK call ends `.catch(medusaError)` (`src/lib/util/medusa-error.ts`), which normalizes to a plain thrown `Error` with a human message — **there is no existing special-case for HTTP 429 anywhere in the codebase** (confirmed no hits for "rate limit"/"429").
  - Because the voucher endpoints (`POST/DELETE /store/carts/:id/voucher`, `GET /store/customers/me/vouchers`) are **custom module routes**, not core Medusa resources, they are **not** available as typed `sdk.store.cart.*` methods — they must be called directly (e.g. via `sdk.client.fetch(...)` or an equivalent request helper), the same way `retrieveCart` calls `/store/carts/${id}` by raw path.
  - No React Query/SWR — all data flows through Server Components + `revalidateTag`; client components track their own `useState` loading/error, no optimistic UI.

### 1.5 Authentication / customer state

- `src/lib/data/customer.ts`: `retrieveCustomer()` reads `getAuthHeaders()`; no token ⇒ guest (`null`). Cart template already branches `!customer && <SignInPrompt/>` for other guest-facing UI. **Corrected finding (verified against the running backend, supersedes an earlier "not gated" claim):** `GET /store/customers/me/vouchers` is **not** public — core Medusa applies `authenticate("customer", ["session","bearer"])` to the wildcard path `/store/customers/me*` (`@medusajs/medusa/dist/api/store/customers/middlewares.js`), which intercepts this custom route regardless of its own handler code. An unauthenticated request returns `401`, empirically confirmed. The frontend does **not** need a dedicated branch for this: `fetchAvailableVouchers()` catches the failure and resolves to `[]`, so a guest simply sees the ordinary empty-list state — see §2 table for the full correction.
- No `x-session-id`-style header exists in the storefront; the backend's dismissal/analytics scoping (SuggestiveSelling side) is unrelated to voucher auth.

### 1.6 Toast / modal / form / loading patterns

- **No toast/notification system exists** (explicit TODO, §1.3). All current "notifications" are ad hoc inline banners:
  - `layout/components/cart-mismatch-banner/index.tsx` — full-width banner, icon + message + inline retry button, `isPending` state. **Closest template for a voucher error/rate-limit banner.**
  - `shipping/components/free-shipping-price-nudge/index.tsx` — has an `inline` (progress card) and a `popup` (dismissible fixed-position card, `useState(isClosed)`) variant. **Closest template for a toast-like "voucher applied!" confirmation** without adding a dependency.
  - `checkout/components/error-message/index.tsx` — trivial inline red text, used everywhere for field errors; the natural place for "invalid code" / validation failures unless a toast is introduced.
- **Modal**: `common/components/modal/index.tsx` (Headless UI `Dialog`, compound `Modal.Title/Body/Footer`, `ModalProvider`/`useModal()`). Not currently used by cart/voucher; candidate for a "replace promotion code?" confirmation dialog (VOUCH-001, per-SRS confirm prompt) or the "available vouchers" list.
- **Forms**: plain `<form action={asyncFn}>` (no react-hook-form). Pending state via `useFormStatus()` inside `<SubmitButton>` (`checkout/components/submit-button`) — the button component the enhanced module's single Apply input should reuse.
- **Loading**: `modules/skeletons/components/skeleton-code-form/index.tsx` already exists (built for the current discount-code form) and `skeleton-cart-totals`, composed into `skeletons/templates/skeleton-cart-page` and rendered by the route-level `cart/loading.tsx`.

### 1.7 Responsive conventions

- Medusa-preset breakpoints (§1.3); cart layout uses `grid-cols-1 small:grid-cols-[1fr_360px]` (mobile-first, `small:` = desktop).
- **No bottom-sheet/drawer primitive exists.** The closest overlay patterns are the center-screen `Modal` and the nav `side-menu` drawer (headlessui sliding panel, nav-specific today). Any mobile "available vouchers" list reuses the center `Modal` (see `WIREFRAMES.md` §5) rather than introducing a new pattern.
- `cart-dropdown`'s popover is desktop-only (`hidden small:block`); mobile has no mini-cart affordance at all today.

### 1.8 Existing test setup

- **None.** No `test` script in `apps/storefront/package.json`, no Playwright/Jest/Vitest config, no `*.spec.ts(x)`/`*.test.ts(x)` files anywhere under `apps/storefront`. The `data-testid`s present in cart markup suggest tests were planned but never implemented in this app. Any voucher UI test coverage is greenfield (framework choice included).

## 4. Consolidated open questions (carried forward from §3, for implementation to resolve before/during the code refactor)

1. **Voucher state hydration on page load/refresh.** `retrieveCart()`'s default field list omits cart-level `metadata`, but the authoritative "is a voucher active" record lives in `cart.metadata.voucher`. Needs a `fields` change (D2) before the UI can restore voucher state after a reload. **Preserved finding:** even once fetched, `cart.metadata.voucher` does not carry `cap_explanation` or `expires_at` — a reload can restore `discount_capped` as a boolean, never the explanation text, unless the backend is changed later to persist it (§2 table).
2. **Interaction with the existing generic promotion UI — RESOLVED.** The earlier open question ("should this reuse `discount-code/index.tsx`, or be a fully separate component?") is resolved in §0: the existing component is enhanced/reworked in place. There is exactly one input, one Apply button, one applied-codes list — never two. The remaining implementation detail is the single-input routing rule (`UX-FLOW.md` §1a).
3. **Toast vs. banner notification pattern — RESOLVED.** No toast system exists; inline messages + the existing `Modal`/banner patterns only (`UX-FLOW.md` D5).
4. **Async revalidation timing.** Because `revalidateVoucherOnCartChange` runs as an async subscriber (not synchronously in the mutating request, a deviation from the original contract), the bounded-refresh strategy in `UX-FLOW.md` §3 defines what the UI does in the gap between a cart mutation's response and the subscriber actually completing — **keep the auto-remove reason text deferred/speculative** unless the backend confirms a metadata channel for it (see `UX-FLOW.md` §3/§7).
5. **Rate-limit UI (EC-10/SEC-02) is unverifiable today** — backend 3.7.x is not implemented. **Resolved:** build the state defensively in the design, but do not implement it as live behavior until the backend ships it **and** until item 12 below is resolved.
6. **"Available vouchers" personalization gap — CORRECTED (was wrongly marked resolved-as-public; still an open product/backend decision).** The endpoint returns all active vouchers for an authenticated customer — not a per-customer assignment — but is **customer-gated, not public**: core Medusa's `authenticate("customer", ["session","bearer"])` middleware on `/store/customers/me*` returns `401` for guests, verified against the running backend (§2 table). The frontend already degrades gracefully (`fetchAvailableVouchers()` catches the 401 and resolves to `[]`, so guests just see the empty-list state, `WIREFRAMES.md` §2.2) — no frontend fix needed. What remains genuinely open: **should the route be changed to be truly public (guests see the same list), or should it stay customer-gated with a real sign-in-to-view state (`WIREFRAMES.md` §2.3)?** That decision belongs to product/backend, not this document. Regardless of the outcome, do not call the list "My vouchers" or otherwise imply personalization it doesn't have.
7. **Mini-cart voucher visibility** — product decision, not a technical blocker; explicitly out of scope for this design (D7).
8. **Mobile bottom-sheet primitive** — none exists; the "Available vouchers" list and replace-confirmation reuse the existing center `Modal` on both viewports instead (resolved, no new primitive needed).
9. **Concurrency signal for voucher-specific operations** — confirm the exact conflict/lock-contention response shape for `POST/DELETE /store/carts/:id/voucher` specifically (the progress log describes a per-cart lock step but doesn't confirm the HTTP-visible error shape on lock contention). Still open.
10. **Placeholder interpolation** — confirm which error `customer_message` templates are pre-filled server-side (confirmed for `VOUCHER_REPLACE_REQUIRED`'s `{current_code}`) vs. which still require client-side template-filling from `details`. Still open.
11. **NEW — single-input routing latency.** Routing a submitted code through "try voucher first, fall back to generic promotion" (`UX-FLOW.md` §1a) means an ordinary generic-promotion code incurs a second network round trip (the voucher attempt, which will 404, before the generic-promotion call runs). Confirm whether this latency is acceptable, or whether a future backend slice should offer a single combined lookup endpoint. Not a blocker for this design, but should be confirmed before or during the code refactor.
12. **NEW — rate-limit / fallback-routing interaction risk (flagged, NOT resolved — backend/API design dependency).** `UX-FLOW.md` §1a's routing rule makes every ordinary generic-promotion code produce a `VOUCHER_NOT_FOUND` response on its way to the generic-promotion fallback. VoucherEngine's brute-force protection design counts only `VOUCHER_NOT_FOUND` toward its rate-limit counter (SPEC §9.3). Once backend rate limiting ships (3.7.x), a naive implementation would incorrectly count ordinary generic-promotion attempts toward voucher cooldown, penalizing customers for typing unrelated promo codes. **This must be resolved on the backend/API design side before enabling live rate-limit UI** — see `UX-FLOW.md` §1a/D13 for the full reasoning and two possible backend-side solutions (a combined apply-discount-code endpoint, or a separate non-counting voucher probe/lookup path). Do not build the rate-limit UI (item 5 above) as live behavior until this is confirmed resolved, even after 3.7.x ships.
